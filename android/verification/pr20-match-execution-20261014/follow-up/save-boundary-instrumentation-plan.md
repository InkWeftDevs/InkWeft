# Save latency: concrete observation boundaries without a library fork

Keep cb7e142's verified search work. The next useful change is an opt-in diagnostic, not a guessed save optimization or a claim that all acceptance gates passed. The existing default-off save hook can be extended with Room/SupportSQLite boundaries to separate queueing, BEGIN, body, outer END and return. Exact private `resumeWith` and invalidation-CAS callbacks are not exposed; name the measured substitutes accurately.

This is a read-only implementation plan. No source, library, test or controller was edited; no build, device, network or CI was run. Local cached dependency bytecode was inspected, including with the installed JDK's `javap`. Kotlin override/Room code-generation compatibility still needs compilation after implementation is separately authorized.

Median paired deltas are respectively **4.4063 ms** and **6.7368545 ms**; these differ from subtracting the two medians. Preserve each seed's 30 ordered saves and the original classifier. The prior causal run's 360 committed saves all crossed threads between `receipt-written` and `transaction-returned`; FULL tail p50 was 3.042/2.682 ms in the two blocks. That is not a commit timer. Its body matcher was not reached by the cancelled FULL reads during the save window, so cb7's matcher gain is not a sufficient explanation of this save tail. See the unchanged `save-return-review.md`, `save-return-raw-review.json` and original causal method10 records. The prior modes have different readiness conditions; their medians are not additive causal coefficients.

The actual local path is Room **2.8.5**, OpenHelper compatibility mode, Requery **3.49.0**, WAL with `synchronous=FULL`, coroutines **1.10.2**. `NoteDatabase.open` sets no driver, query/transaction executor, query coroutine context or auto-close. Room's builder defaults both executor references to `ArchTaskExecutor.getIOThreadExecutor()`, then wraps transaction work in its own serial `TransactionExecutor`.

## Minimal first implementation

Use a per-database nullable diagnostic sink, installed only for a dedicated synthetic test before any worker starts. Off means the existing factory/executors and save path are returned directly: no clocks, event allocation, thread-local access or extra SQL in the normal path. Keep one small event/sink type, not a general tracing framework. Its recorder must never throw into a transaction: on capacity/recording failure set an invalid/overflow flag and fail the diagnostic after teardown, preserving any primary database/cancellation error.

Proposed files:

1. `android/data-local/src/main/kotlin/org/inkweft/data/NoteDatabase.kt`: nullable observer, overrides around `beginTransaction`, `setTransactionSuccessful`, `endTransaction`, and a diagnostic-only delegating `transactionExecutor` getter. Return `super.transactionExecutor` unchanged while disabled. While enabled, wrap the **existing Room serial executor**, not a new pool/serial queue; submit exactly once and execute the original Runnable exactly once. Room's legacy `startTransactionCoroutine` calls that getter, confirmed by its bytecode. This records arrival before Room's serial queue and entry into the selected executor thread. It does not instrument every generated-DAO coroutine dispatch; state that scope explicitly.
2. `android/data-local/src/main/kotlin/org/inkweft/data/PreservingOpenHelperFactory.kt`: accept an optional sink only from the diagnostic opening path. Enabled helpers return a stable `SupportSQLiteDatabase by delegate` wrapper; disabled helpers return the original Requery database. Override the begin variants, `setTransactionSuccessful`, `endTransaction`, and pass through all other operations. Cache per underlying database identity and reset on close/reopen. Do not change any corruption callback, sidecar lock, database name, first-open behavior, PRAGMA, recovery or migration policy. Install before opening, not midway through a transaction. Callback setup can continue to receive the same original database; start diagnostic collection after warm setup. The Room connection pool's driver obtains its database through the helper, so normal runtime DAO transactions use the wrapper. This detail must be confirmed by the new native trace, not presumed from wrapper construction alone.
3. `android/data-local/src/main/kotlin/org/inkweft/data/NoteRepository.kt`: retain existing `waiting-writer`, `writer-acquired`, staged body and `transaction-returned` hooks unchanged. The outer `RoomDatabase.setTransactionSuccessful` entry provides a better successful body-return boundary than `receipt-written`: Room invokes it after the block has produced its result, before END. Do not replace `withTransaction`, the DAO chain, or its early conflict/replay returns.
4. New `android/data-local/src/androidTest/kotlin/org/inkweft/data/LibrarySaveBoundaryDiagnosticsTest.kt` with a small test recorder/helper if needed. Reuse committed synthetic fixture logic and explicit mode labels. The original `KvmLibraryPairProbe`, `LibraryReadPerformanceTest`, thresholds and public 30-sample windows stay byte-identical. Existing `LibrarySaveCausalTest` can remain historical; no new fields should silently change its frozen schema.

At the Room and SQLite layers, use distinct events and track nesting per database/thread. A nested DAO end is not an outer durable commit. Only pair depth1→0 database END events; record unsuccessful/throwing END and an outer-success-requested flag without inventing a commit. On BEGIN failure do not increment depth. On END failure preserve the delegate exception and mark tracing incomplete. An unexpected depth, a yield/re-entry, or a missing pair is an invalid trace, not a zero-duration operation. Do not introduce extra `inTransaction()` probes merely for timestamps; use recorded depth and the calls Room already makes.

## Event table and exact interpretation

| Events | Place | What the interval means |
|---|---|---|
| `save-request` | Existing waiting-writer hook on caller | Start of the requested save, before Room dispatch |
| `writer-submit`, `writer-run-enter`, `writer-run-exit` | Wrapper outside `super.transactionExecutor` | Submit→run-enter includes Room serial queue and executor scheduling. Run entry is a thread acquired for the task, **not** a SQLite writer lock acquired. Run exit is not caller resumption. |
| `room-begin-enter/exit` | `override beginTransaction` around exactly one `super` call | Executor-thread Room BEGIN envelope, including trigger synchronization before the database begin |
| `sqlite-begin-enter/exit` | Delegating beginNonExclusive/begin wrapper, outer depth | Connection acquisition/SQLite BEGIN and lock wait as one observable envelope. In WAL mode Room calls nonexclusive, which Requery turns into BEGIN IMMEDIATE. Native lock wait and pool acquisition remain combined. |
| `writer-acquired` | Existing first line of transaction body | Body entry after Room's begin completes |
| `room-success-enter/exit` | Override setTransactionSuccessful around `super` | Entry follows body result construction. Success merely marks the transaction; it is not a commit. |
| `room-end-enter/exit` | Override endTransaction around `super` | Outer Room END envelope including post-database invalidation request |
| `sqlite-end-enter/exit` | Outermost delegate endTransaction | Synchronous native COMMIT/ROLLBACK **plus connection release**. For a subsequently verified committed save with unchanged FULL, successful return is the SQLite commit-return boundary. It is not a separately measured fsync or power-loss test. |
| `transaction-returned`, caller save-end | Existing caller hook/test | The coroutine has actually resumed and returned to the caller |

On a successfully paired save, report per-sample disjoint wall-clock segments such as request→submit, submit→worker entry, worker→Room BEGIN, Room pre-BEGIN, SQLite BEGIN, body, success/end prologue, SQLite END, Room post-END, and Room-end-exit→caller-return. The final segment still contains Room context/continuation machinery plus scheduling. Do **not** subtract `writer-run-exit` from caller-return: the caller can run before the executor Runnable finishes unwinding. Use same-thread CPU differences only when both endpoints have the same thread ID; otherwise CPU is null. Even same-thread counters on a suspended event loop include intervening work and must not be called exclusive body CPU.

## What refresh/resumption can and cannot expose without a fork

`RoomDatabase.internalEndTransaction` calls SupportSQLite END, then `inTransaction()`, then `InvalidationTracker.refreshVersionsAsync()` for the outer transaction. Therefore `sqlite-end-exit → room-end-exit` isolates the Room post-END envelope containing refresh-request/coalescing/launch overhead plus those small checks. It does not await the refresh job. The trigger tracker's scheduled/completed callback fields and pending-CAS are private; replacing the tracker would lose generated table maps/state and is not a minimal wrapper. Do not replace it, reflectively mutate callbacks, or copy Room's internalEndTransaction implementation.

If that Room post-END or final return segment dominates, two **additional opt-in diagnostic-only wrappers** can refine it without new threads or changing public tests:

* At diagnostic database construction only, provide a query-executor wrapper around the same `ArchTaskExecutor.getIOThreadExecutor()` and explicitly keep the transaction executor's underlying delegate equal to that default. Record executor `execute` entry/return and Runnable entry/exit. Tag a submission made synchronously while the same thread is inside the traced outer Room END after SQLite END as `refresh-executor-submit`; the inspected Room path has only the refresh launch there. This is an actual executor-submission event, not the private CAS. A missing submit is compatible with coalescing and must not be presented as a measured zero-cost refresh. Runnable events describe dispatch segments, not necessarily an entire suspending refresh job. Merely overriding `queryExecutor`'s getter is insufficient: Room builds its refresh coroutine scope from its internal executor field during init.
* Around only the diagnostic save caller, use a narrow `CoroutineDispatcher` delegate to the existing `Dispatchers.IO`, preserving `isDispatchNeeded`, `dispatch` and `dispatchYield` and never adding a Job, queue, thread or delay. Record `caller-dispatch-submit` and the wrapped Runnable entry, tagged by the diagnostic coroutine context's sample token. The resume dispatch following the identified Room END gives a measurable dispatch→caller-run delay. It is still **not** the exact private `CancellableContinuation.resumeWith` invocation. A dispatcher wrapper changes interceptor identity/observational overhead, so keep it in a separately labelled arm and require cancellation/exception/context tests before interpreting it. If no unique dispatch can be associated, retain a null result rather than selecting a convenient event.

The minimal first implementation does not need these two wrappers to separate SQLite END from the cross-thread return tail. They are only justified if that first split leaves the dominant interval unresolved. No no-fork plan can honestly promise the private CAS timestamp, the exact internal resumeWith timestamp, native fsync-only duration and connection-release-only duration from the public API wrappers above.

Do **not** use SQLiteTransactionListener.onCommit as a durable-completion callback: cached Requery endTransactionUnchecked invokes it before the native COMMIT and before releasing the connection. Do not use Room QueryCallback as an after-statement timer: it is an interception callback dispatched through its own configured context/executor and also exposes bind arguments. No query/body/ID logging is needed here.

## Correlation, fixture and correctness constraints

Use `(seed, window, sampleIndex)` and a monotonic diagnostic transaction/task ordinal, never real command IDs or titles. A diagnostic ThreadContextElement may carry the sample token without replacing its Job/dispatcher; the inspected Room runnable passes the caller context minus ContinuationInterceptor into runBlocking, so the token can survive the writer transition. Capture the token at executor submission, restore/remove it in finally, and distinguish unrelated index/refresh work from the measured save. A shared global current sample alone is not adequate: concurrent writers or a previous executor unwind could be attributed to the next save.

Every event should contain an enum stage, task/outer-transaction ordinal, nesting depth, monotonic wallNs, threadId, optional threadCpuNs and a small outcome enum. Bounded per-window memory, explicit droppedEvents/traceInvalid, and emission only after timing/joins. No SQL text, bind values, database paths or arbitrary exception strings. Event recording must not acquire a database lock, suspend, wait for a peer, serialize JSON, emit instrumentation output, run a checkpoint, or alter a cancellation signal.

For direct-p95, the next diagnostic must actually reproduce the original **single cold direct read concurrently with 30 saves**; the prior READS_ONLY mode restarts reads on invalidation and is not that window. Separately reproduce the original observe/index-started 30-save window. Freeze the same 500-book/20k-page contents, seeds4101–4104, readiness and saves before execution; report direct/observe separately. A small first scope can use one existing seed to locate the boundary, but it is diagnostic only and cannot close any four-seed public gate. If a B→C1 causal difference is claimed, instrument B and cb7 with the same backportable hooks/data contract; a candidate-only trace locates candidate cost but does not establish which version caused it. Do not turn diagnostic p50 into a replacement acceptance sample.

Required implementation verification before trusting events: disabled path preserves original behavior and emits nothing; one true outer BEGIN/END pair despite nested DAO calls; cancellation before queue entry and inside body rolls back; exception/failed END/replay/conflict preserve results and original exceptions; continued save and reopen recover normally; trace overflow fails evidence without aborting a healthy save. Retain existing command-id idempotency, stale-editor, reopen/history, concurrent author and cancellation Room tests. Wrapper delegates cannot force-stop a job, remove invalidation, delay durability, change executor parallelism, or manually schedule an extra refresh.

Interpretation is predetermined: a large submit→worker segment points to queue/scheduling exposure; a large BEGIN envelope to connection/SQLite begin exposure; a large same-thread body to author SQL/application work; a large END envelope to commit/release exposure; a large post-END Room segment to coalescing/scheduling overhead; a large remaining return segment needs the optional caller-dispatch observation. Wall-minus-CPU alone does not identify fsync versus kernel scheduling. Preserve every outlier and relate intervals for that exact save; medians of components do not sum to the median save.

No optimization is selected by this plan. The next code choice should follow the measured dominant boundary while keeping cb7's search gain and every original save/durability/freshness assertion.
