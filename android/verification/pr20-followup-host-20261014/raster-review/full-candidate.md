# Smallest full-path candidate and exploratory test

This is a source review and proposal only. No change has been implemented or benchmarked. B→C1 eight-layer full remains the frozen screening signal.

The extra work is real and lives in `InkRepository.visitVisible`, not only the append metadata timer. In current `InkRepository.kt:319–369`, each cache-bearing pass performs a separate epoch SELECT alongside the existing page revision check; checks regions/allowed/omitted; builds reused and missing collections; then, even when all strokes missed the cache, makes `snapshot.strokes.associateBy` and reconstructs another list through batch.map/getValue. Finally it checks page, epoch and authoring revisions again. Full/new caches have zero hits but still populate the cache. For the eight-layer 321-stroke fixture, each layer has one data batch, an empty terminating metadata query and a final check: **24 extra epoch reads are predicted from the source**, to be measured rather than reported as observed SQL counts. The B path lacked these cache operations. Conversely native per-stroke reuse can save little when a stroke reaches only one dirty tile; the append counter is not a full-phase native count.

The lowest-risk candidate is one all-miss branch in `visitVisible`, after the existing exact snapshot-revision and ordered-ID equality check. When `cache != null && reused.isEmpty()`, iterate `snapshot.strokes` in the already-validated batch order, `cache.put(stroke,batch[index].spatialKey)`, then pass `snapshot.strokes` directly to visit. Preserve the existing mixed-hit branch. This removes the decoded associateBy, reconstructed list and keyed lookups on the cold full path while retaining cache insertion, eviction/weights, cache-hit accounting, epoch checks, region filtering, payload budget retries, cancellation and paint cursor order. It is approximately 6–10 lines in one production function. The visitor currently only iterates these strokes; no source authority or layer/transform behavior changes. Do not predict that this allocation reduction explains all 39 ms.

A separate, second candidate would combine the existing revision lookup and cache epoch lookup into one SQL statement within each current transaction (including the final check), retaining both values and identical absent-row defaults. This can remove cursor/SQLite calls while keeping the same snapshot checks. It needs explicit absent-page/epoch, same-revision-mask, revision-race and final-check tests. Do not simply skip cold-cache epoch checks: masks can change between batches at the same page revision, and the current final epoch check rejects a mixed frame. Do not combine both candidates initially because that loses attribution.

Minimum exploratory comparison: **C1 control versus the single all-miss candidate, seeds 4101 and 4102, four diagnostic method calls total**, order C1→candidate for 4101 and candidate→C1 for 4102. Use existing `RasterCausalDiagnosticsTest#oneFourEightLayerAppendReportsFrameStagesAndMatchesColdFrames`, its default-off C1 `RasterFrameDiagnostics` and read/metadata observers on both sides. Change only the diagnostic test's seed allowlist to permit these two seeds; preserve the entire 1/4/8 setup and first/local/full/hidden-local/hidden-full sequence, logical fixture hashes, exact cold-pixel assertions, layer revisions and owned Job joins. Select `role=full,phase=full,layers=8` during analysis, while retaining all output. No new B hook is necessary to test this isolated C1→candidate change. Existing stage times localize metadata/worker/prepare/publication/ready intervals and actual native/read work; they do not directly count allocations or measure cache-only CPU, so a null result is informative rather than a reason to add broad tracing.

The experiment needs two app identities (four app/appTest APKs; data APK from the final source can be shared only as a separate source-bound result). If merged into an already planned final-source job, the marginal cost is one additional app build, roughly 8–12 minutes, plus four short diagnostic calls/install transitions (estimate 1–3 minutes); actual building dominates. The six strict cleanup calls remain once on the final source and need not be duplicated on the control. This four-call exploration cannot close the original B→C1 four-pair gate or establish a percentile. A worthwhile candidate would still need the original four-pair public comparison and relevant unchanged guards before acceptance; a null result should stop this candidate rather than trigger retries.

If attribution specifically requires B, insert only matching default-off frame-stage/native timing around B's own loops and matching metadata/read clocks, keeping B's per-tile native construction and original source behavior. That requires a distinct Bdiag identity; do not copy C1's repository or raster wholesale. This costs an additional identity/build and is not the first experiment proposed here.
