“提交前时点覆盖”仍严格沿用`saveStart <= before-batch-commit <= saveEnd`；“DELETE窗口交叠”另用`max(saveStart,deleteStart) < min(saveEnd,deleteEnd)`。前一公式本身不能证明DELETE循环交叠，本次后两项独立记录也成立。DELETE窗口包含observer通知、时钟和callback开销，不等于纯SQL执行时间。

每条均记录并通过源断言的revision2→3、最终标题/正文、最新来源1281及其snapshot字节保留。两连接writer设置均是1024/FULL(1)/WAL/synchronous2。本轮7个前置正确性方法1–7也均由日志回执标PASS，但它们不是旧`HistoryCollectionTest`门控活根/损坏/取消用例；不能把旧GC安全套件说成本轮已重跑。

同Room的30次均首批删256后延期、收尾删1024。对应下一批guard全部是`data_version delta=0, changes delta=3`。这直接观测到同一writer连接上的变更分量在作者写入后改变，与保守延期合同一致。

另一Room：23次首轮删256、3次删768、4次删完1280；相应收尾删1024/512/0。26次延期的guard中，17次`data_version delta=1`、9次delta=2，changes delta均0；delta=1其中3次发生在sequence768，其余14次在256。数据支持外部连接变更被侦测，**不能假设每次提交data_version恰好+1**。4次不延期的整轮GC在作者调用仍未返回时完成，守卫尚未观察到作者已提交的改变；没有日志显示守卫越过了已观察到的变更继续删除。

本夹具作者只rename笔记，没有新建来源活根；其内容/保留集合断言和上述guard证据成立，但不能用本夹具替代已有“新增活根300必须保留”的确定性安全测试。

## 跨 Room 尾部：已见现象与未定原因

另一Room的4个整轮首删1280样本为9、17、21、24，保存耗时分别57.277407、37.076502、36.345268、56.665894ms。样本9和24的保存调用覆盖全部5个真实提交的GC删除批次：

| 相对保存调用开始 | sample9 | sample24 |
|---|---:|---:|
| 最后DELETE窗口结束 | 33.392766 ms | 33.958673 ms |
| 最后GC删除事务返回 | 34.575846 ms | 35.026518 ms |
| 首轮GC调用结束 | 36.503077 ms | 36.751941 ms |
| 作者BEFORE_RENAME_RECEIPT | 56.023985 ms | 55.448901 ms |
| 作者事务返回 | 57.209159 ms | 56.559255 ms |
| 保存调用返回 | 57.277407 ms | 56.665894 ms |

这说明请求可能跨多个GC短事务仍未完成，且较慢两例从GC最后删除事务返回到作者receipt前还有约20–21ms。**这些区间不能直接命名为锁等待。** `writerEntryNs`和`pureSqliteLockWaitMs`均为null，没有作者进入原rename事务的时间点，Room排队、线程调度、SQLite竞争/重试及作者SQL/提交耗时尚不能拆开。不能仅凭约50ms台阶断言SQLite busy backoff，也不能证明某个调度器优先级是唯一原因。

同Room和另一Room是本次顺序执行的两个连接模型，缺少同场景基线；较高的跨Room尾部是本候选诊断观察，不能称B→C1回退或改善。5秒watchdog均未触发，但5秒不是性能门槛。

## 仍开放的范围与最小下一步

1. **自然到达暴露仍未闭合。** 旧自然after-scan诊断的0/30仍原样成立；本轮条件到达不会估计普通用户保存碰到DELETE的概率。
2. **等价基线竞争尾部比较仍缺。** 本轮只有一个候选的一次条件到达诊断，没有相同hook、夹具、SQLite环境和配对顺序的baseline，不能作正式性能门槛判定。
3. **跨Room尾部归因仍缺writer入口。** 如需继续定位，最小追加测量是在原rename的`withTransaction`块首行加默认关闭时间标记，不外包新事务、不暂停GC、不改批量或阈值。该时间差最多分解为writer取得前累计延迟与之后SQL/提交，仍不是纯SQLite锁等待。本轮未实现或运行这项追加。
4. **没有已证实的最小产品修复。** 现有guard按记录工作，保存/内容/保留集合都正确。当前证据不足以合理选择缩批、人工延时、跳过guard、跨Room统一调度或改变SQLite策略；这些会改变成本/语义，不能为本次样本尾部直接引入。先保持生产行为，若确需优化跨Room尾部，再用上述最小测量与等价对照区分机制。
